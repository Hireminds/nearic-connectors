# Предложение контракта коннектора и Nearic Service

Один версионируемый HTTPS-интерфейс для обоих способов установки. Имена ниже обозначают операции, а поля показывают минимальное согласуемое содержание. Синтетические значения `install-demo`, `thread-a` и `box-demo` служат только для примеров.

| Операция | Вход | Результат |
| --- | --- | --- |
| Вход | OAuth Device Authorization Grant и доказательство владения ключом при регистрации экземпляра | Разрешение аккаунта, связанное с экземпляром и ключом. Пользовательский код и авторизация имеют ограниченный срок. |
| Начать привязку | Разрешение, подтверждённый адрес текущего разговора, одноразовое доказательство запроса | Одноразовое намерение и сведения для подтверждения. Владелец видит разговор, выбирает BOX из своего аккаунта и явно подтверждает операцию. Название разговора, если доступно, служит подсказкой. |
| Подтвердить и узнать итог | Явное подтверждение владельца под тем же аккаунтом, выбранный BOX, намерение и ожидаемое поколение. Для чтения итога из коннектора — исходное разрешение и доказательство | Текущая привязка и результат намерения. Повтор подтверждения возвращает сохранённый итог без повторного применения. Если привязка уже изменилась, интерфейс позволяет увидеть актуальное состояние и начать новое подтверждение. |
| Запросить статус | Разрешение, подтверждённый текущий адрес и доказательство вызова. При нескольких BOX в этом разговоре — выбранное устройство. Параметры инструмента не содержат адреса или учётных данных | Версия и время работы из текущей операции либо различимый отказ, отсутствие привязки, недоступность или тайм-аут. |
| Отозвать | Подтверждение владельца для конкретного разрешения | Сервис прекращает авторизацию этого экземпляра. BOX остаётся зарегистрированным и подключается самостоятельно. |

## Доказательство адреса

- Адаптер формирует адрес из проверенного канала запуска и метаданных конкретного вызова. Владелец подтверждает выбор для уже зафиксированного адреса. Проверка источника адреса обязательна независимо от интерфейса подтверждения.
- Предложение для сервиса — подписывать запрос ключом экземпляра через HTTP Message Signatures и включать метод, целевой URI, дайджест тела и ограниченные по времени параметры подписи с одноразовым значением. Дайджест связывает доказательство с адресом и содержимым операции. Токен связан на сервисе с тем же ключом. Сервис проверяет подпись, срок, одноразовость и активность разрешения, затем проверяет полномочия. Повтор после потери ответа использует свежую подпись и прежний ID намерения. Параметры профиля подписи и допустимое расхождение часов согласуются до реализации. [RFC 9421](https://www.rfc-editor.org/rfc/rfc9421), [RFC 9530](https://www.rfc-editor.org/rfc/rfc9530).
- Локально проверить две меры вместе. Подписывающий компонент хранит ключ вне доступа агентского sandbox. Локальный вход принимает запросы только из канала, открытого проверенным хостом, с проверкой личности запускающего процесса на уровне ОС. Кандидаты на проверку — отдельный процесс с хранилищем учётных данных ОС и проверкой идентичности запускающего клиента на macOS, отдельный системный principal и ограниченный IPC на Linux. Прямой запуск бинарника из shell, подмена декларации, унаследованный дескриптор и обращение к IPC из агента должны давать отказ. Способ установки этих мер входит в техническое решение после проверки, поскольку дополнительные системные права меняют сценарий установки.
- Ключ зарегистрированной установки удостоверяет делегирование адаптеру. Если достоверность канала к Codex не подтверждается, сервису нельзя обещать проверяемый адрес для этой платформы. Компрометация доверенной ОС или администратора находится за пределами данной границы.

## Живой статус

При принятии операции сервис фиксирует её BOX, поколение и адрес. Только совпавший живой ответ до дедлайна даёт успех. При известном отсутствии связи сервис может сразу вернуть `device_unavailable`. Если известна только просрочка ожидания, результат — `no_fresh_response`. Отказ по доступу имеет приоритет над диагностикой устройства. Авторизованный запрос из другого разговора даёт `binding_required` без раскрытия адреса актуального разговора. Отозванный доступ даёт `access_revoked`, неподтверждённый контекст — `context_unverified`. Локальное отсутствие метаданных тоже отображается как отказ с причиной отсутствия проверенного контекста.

Если с разговором связаны несколько BOX, пользователь выбирает устройство из доступных в этом разговоре. Коннектор не выбирает BOX молча. Сервис проверяет выбранное устройство по тому же адресу и разрешению.

MCP-поверхность предлагает один проверочный инструмент `nearic_status`. Начало привязки относится к отдельному действию настройки, которое использует ту же подтверждённую адресацию. Управление подтверждением и отзывом происходит с участием владельца. Сервисная граница требует только статуса и управления разрешением и привязкой. Адрес разговора и разрешение агента не передаются BOX.

## Предложение общих полей для технического ревью

Профиль рассчитан на общее ядро Desktop и удалённого CLI. Начальные параметры предложены для технического согласования. Для привязки, живого статуса и получения их результатов обязательны проверяемый адрес и действующее разрешение. Формат `contextProof` и источник адреса открыты.

### OAuth Device Authorization Grant

Начало входа и опрос токена используют `POST` с `application/x-www-form-urlencoded`.

| Событие | Поля и предложенные значения | Действие ядра |
| --- | --- | --- |
| Начало входа | Запрос с `client_id`, запрошенным `scope`. Ответ с секретным `device_code`, отображаемыми `user_code`, `verification_uri`, необязательным `verification_uri_complete`, `expires_in=600`, `interval=5` секунд | Показать адрес и пользовательский код, сохранить секретный код только в процедуре входа. Учёт срока начинается при получении ответа и отслеживается монотонными часами. |
| Опрос | `grant_type=urn:ietf:params:oauth:grant-type:device_code`, `device_code`, `client_id` | Первый опрос через `interval`, последующие с соблюдением актуального интервала. |
| Ожидание | OAuth `authorization_pending` | Продолжать до истечения срока. |
| Замедление | OAuth `slow_down` | Увеличить интервал на 5 секунд для всех последующих опросов. При сетевом тайм-ауте увеличить интервал экспоненциально. |
| Успех | `access_token`, `token_type`, `expires_in`, фактически выданный `scope`, непрозрачный `grantId`. `refresh_token` выдаётся только при согласованной поддержке обновления | Завершить вход, сохранить разрешение в защищённом хранилище. Политика обновления и тип токена, связанного с ключом, требуют согласования. |
| Отказ или истечение | OAuth `access_denied` либо `expired_token` | Завершить процедуру с различимой причиной. Локальная отмена прекращает опрос. Новая попытка получает новый код. |

Срок 600 секунд и интервал 5 секунд — предлагаемые настройки сервиса. Ядро использует значения ответа. Ответ успеха также содержит `grantId`. Поле `grantId` — расширение Nearic для управления разрешением. Вход сам по себе не создаёт привязку. Отзыв определяется сервисом при каждом защищённом обращении. Идентификация экземпляра и доказательство владения ключом согласуются отдельно от стандартных полей device flow. [OAuth Device Authorization Grant](https://www.rfc-editor.org/rfc/rfc8628).

### Подтверждение привязки

Предлагается сохранить шаг выбора зарегистрированного BOX и явное подтверждение владельцем в обоих клиентах. Место подтверждения в интерфейсе следует согласованному сценарию. Предыдущая формулировка о браузерном подтверждении описывает технический кандидат.

1. Начало намерения принимает `operation=prepare_bind`, `deviceId`, `contextProof`, `requestId` и `expectedBindingId`. При первой привязке `expectedBindingId=null` явно означает отсутствие действующей привязки. Сервис фиксирует проверенный адрес, grant и выбранный BOX. Ответ содержит `intentId`, `expiresAt` и сведения для отображения выбранных BOX и разговора. Предлагаемый срок намерения — 300 секунд.
2. После явного подтверждения отправляется `operation=bind`, `intentId`, `requestId`, `expectedBindingId` и новое действующее `contextProof`. Ядро сверяет неизменность выбранного адреса с намерением. Сервис атомарно проверяет владельца, grant, намерение и предусловие поколения, затем заменяет привязку. `bindingId` уникален для каждого нового поколения и служит токеном сравнения без разбора на клиенте.
3. Ответ успеха содержит `requestId`, `outcome=ok`, `bindingId`, `deviceId`, `confirmedAt`. Повтор с тем же `requestId` и тем же смысловым содержимым возвращает исходный итог при действующих полномочиях. Повтор с изменённым содержимым даёт `request_conflict`. Доказательство при повторе обновляется и не входит в сравнение смыслового содержимого.
4. Изменение текущей привязки до подтверждения даёт `binding_conflict`. Истёкшее или отменённое намерение даёт `confirmation_expired` или `confirmation_cancelled`. Неуспешное подтверждение сохраняет текущую привязку. Отмена завершает только ожидающее намерение. При гонке отмены и фиксации сервис возвращает фактически сохранённый итог.
5. После потери ответа ядро читает итог по `requestId` с актуальными полномочиями и доказательством. Возвращаются отдельно результат исходного подтверждения и актуальный `bindingId`. Повтор старого подтверждения после более нового переключения не применяет старую привязку заново.

Предлагается хранить ключ идемпотентности 24 часа с первого принятия запроса. В ответе передавать `retryUntil`, повтор не продлевает срок. После него ядро сверяет актуальную привязку и запрашивает новое явное подтверждение при необходимости. Срок требует согласования с сервисом.

### Живой статус, дедлайн и повтор

| Поле | Предложенная семантика |
| --- | --- |
| `operation`, `deviceId`, `requestId`, `contextProof` | `get_status`, выбранный BOX, стабильный ID одной проверки и новое доказательство каждого обращения. Разрешение передаётся защищённым транспортом. |
| `acceptedAt`, `deadlineAt`, `retryUntil` | Сервис фиксирует дедлайн один раз при первом принятии. Начальный бюджет 10 секунд взят из проекта границы BOX. Результат и ключ повтора предлагается хранить 24 часа. Повторы не продлевают дедлайн и срок хранения. |
| `bindingId` | Снимок поколения при принятии. Вместе с grant, BOX и проверенным адресом остаётся частью операции до завершения. |
| `outcome=pending`, `retryAfterMs` | Нетерминальное состояние принятой операции. Предлагается опрос через 1000 мс, далее по ответу сервиса. Чтение итога не создаёт новую команду BOX. |
| `outcome=ok`, `firmwareVersion`, `uptimeMs` | Терминальный живой результат с совпавшими устройством и запросом. `uptimeMs` — целое неотрицательное время работы в миллисекундах. |

После сетевого обрыва повтор отправляет прежний `requestId` и прежнее смысловое содержимое со свежим доказательством. Сервис возвращает сохранённый итог или состояние исходной операции. Другая полезная нагрузка с тем же ID даёт `request_conflict`. Пока текущая привязка уже переключена, чтение ранее принятой операции A допускается только её исходному адресу с действующим grant. Создание новой операции из A отклоняется. Новый живой запрос после терминального исхода получает новый `requestId`.

Ядро ограничивает одно HTTP-ожидание 5 секундами и повторяет временный сетевой сбой с задержками 1, 2, 4 секунды, затем до 5 секунд с разбросом, учитывая `Retry-After` и оставшийся общий бюджет. Предлагаемый общий клиентский бюджет — принятый бюджет операции плюс 5000 мс для доставки результата. Тайм-аут MCP должен покрывать этот бюджет. Если клиент исчерпал свой бюджет без ответа сервиса, он показывает отсутствие полученного свежего ответа с локальной причиной `transport_timeout`. Он может уточнить итог по прежнему ID при восстановлении связи в пределах `retryUntil`.

Сервис завершает ожидание в `no_fresh_response` по `deadlineAt`. При переключении переданная BOX операция может завершиться в исходном разговоре до дедлайна при действующем grant. Неотправленную операцию старого поколения сервис отменяет с `binding_required`. Отзыв закрывает ожидающие операции и закрывает чтение сохранённых результатов с `access_revoked`. Поздний, повторный или относящийся к другому BOX ответ не меняет терминальный результат. Дедлайн, повтор и хранение результата одинаковы для Desktop и CLI.

### Общие исходы

| Исход | Значение для ядра |
| --- | --- |
| `ok` | Успех привязки либо живой ответ на текущую операцию в зависимости от типа запроса. |
| `access_revoked` | Разрешение отозвано, требуется новый вход и подтверждение разговора. |
| `context_unverified` | Сервис или адаптер не подтвердил адрес. Операция отклонена. |
| `binding_required` | Для этого адреса и BOX нет действующей привязки. |
| `binding_conflict` | Предусловие текущего поколения при переключении не выполнено. |
| `device_busy` | Устройство временно занято. Для нового запроса требуется новый ID. |
| `device_unavailable` | Сервис располагает актуальным свидетельством недоступности BOX. |
| `no_fresh_response` | Серверный дедлайн истёк без подходящего живого ответа. |
| `access_denied` | Общий отказ по полномочиям, включая чужой BOX. В OAuth это также стандартный отказ пользователя от входа. |
| `request_conflict` | Один ID повторён с другим смысловым содержимым. |
| `confirmation_expired`, `confirmation_cancelled` | Намерение завершено без применения новой привязки. |

Для защищённого запроса сначала проверяются разрешение и доказательство адреса, затем право на BOX и применимая привязка. Диагностика чужого устройства и адрес активного чужого разговора не раскрываются. Назначение HTTP-кодов и MCP-представление ошибок остаются предметом технического ревью.

## Результат сверки предложений

| Область | Совпадение двух предложений | Точное расхождение или недостающий выбор |
| --- | --- | --- |
| OAuth | Отдельное отзывное разрешение, браузер на другом компьютере, проверка при каждой операции | Сервис оставлял браузерный OAuth-поток открытым. Коннектор предлагает RFC 8628. Все поля device flow, время жизни, обновление и привязка к ключу требуют подтверждения сервисом. |
| Привязка | Явное подтверждение владельцем, одно активное поколение BOX, предусловие поколения, идемпотентный повтор | Сервис использует `expectedBindingId` и `requestId` в `bind`. Здесь приняты эти имена. Намерение `intentId`, его 300 секунд, двухшаговый обмен и чтение итога — дополнение коннектора на ревью. Браузерное место подтверждения ранее предлагал только коннектор. |
| Живой ответ | Текущий запрос, исходный адрес и поколение, успех со свежим ответом | Приняты сервисные имена `requestId`, `firmwareVersion`, `uptimeMs`. Поля дедлайна, `pending`, интервалы и сроки повторов требуют сверки с сервисом. |
| Ошибки | Различимы отзыв, неподтверждённый адрес, отсутствие привязки, конфликт, недоступность и отсутствие свежего ответа | Прежние `response_timeout`, `binding_missing` и общий `access_denied` заменены соответственно на `no_fresh_response`, `binding_required`, раздельные `access_revoked` и `context_unverified`. Сервисный `device_busy` добавлен. HTTP/MCP-отображение открыто. |
| Переключение и отзыв | Новые вызовы старого адреса отклоняются. Принятая операция сохраняет исходный адрес. Отзыв лишает ожидающую операцию права на результат | Поведение отзыва уже совпадает с предложением модели коннектора. Детали гонки отзыва и выдачи сохранённого результата требуется определить общей транзакционной границей. |
| Проверяемость адреса | Проверка обязательна на bind и каждом вызове. OAuth отдельно проверяет полномочия Nearic | Формат `contextProof`, способ удостоверить источник и профиль ключа установки открыты. Поля и исходы выше применимы после успешной проверки любым согласованным способом. |

Сверка описывает семантику прочитанных проектов контракта. Принятые здесь имена и предложенные числа передаются на техническое ревью. Они не означают двустороннее утверждение реализации.
