# Технический план общего коннектора Nearic и адаптера Codex

**Ветка** — `001-common-connector`
**Дата** — 24 ноября 2026 г.
**Статус** — предложение на техническое ревью
**Вход** — [согласованная продуктовая спецификация](spec.md)

## Резюме

Поставить один исполняемый файл Nearic на каждый поддерживаемый хост. Плагин Desktop и пакет для удалённого CLI запускают локальный командный интерфейс и stdio MCP из одной сборки ядра. Codex-адаптер извлекает адрес из метаданных конкретного вызова от хоста. Сервис подтверждает привязку в браузере владельца, проверяет адрес и разрешение при каждой проверке и адресует живой запрос BOX.

## Технический контекст

- **Язык и зависимости.** Go, одна поддерживаемая стабильная ветка для выпуска, официальный Go SDK MCP как кандидат. Проверка сохранения `params._meta` в обработчике обязательна при выборе версии SDK. OAuth и HTTPS-клиент в общем ядре.
- **Хранение.** Сервис хранит разрешения, привязки и операции. Хост хранит отзываемый доступ и ключ экземпляра в изолированном локальном хранилище. Общего секрета в дистрибутиве нет. Способ изоляции проверяется отдельно для каждой поддерживаемой платформы.
- **Кандидат для Linux CLI.** Именованный профиль Codex ограничивает доступ команд к ключу и файлам установки, а доверенный stdio MCP подписывает адрес хоста. Стенд подтвердил отдельные операции изоляции. Необходимость специального профиля, его установка и гарантии при наличии других инструментов требуют технического ревью. [Прогон Linux](research.md#кандидат-изоляции-codex-cli-на-linux)
- **Платформы.** Первый прогон Desktop на macOS arm64 с локальным исполнением и SSH CLI на Linux amd64. Это матрица для первого прогона. Версии клиента и ОС для поддержки объявляются по результатам. Поддержка облачных разговоров и дополнительных платформ требует подтверждения.
- **Поставка.** Один тег выпуска GitHub Releases, Linux-архив с бинарником и Desktop-архив с локальным персональным marketplace, плагином и бинарником. Манифест и `.mcp.json` запускают бинарник через stdio. Инструкция установки содержит контрольную сумму, версию и проверку активации. См. [решения по поставке](research.md#поставка).
- **Проверки.** Модульные проверки ядра, проверка контракта сервиса, проба клиентов с синтетическими разговорами и отдельная приёмка на BOX. Сервис ограничивает время ожидания живого ответа. Конкретный бюджет согласуется с сервисом и проверяется против тайм-аута инструмента клиента.

## Проверка конституции

- Одно ядро владеет авторизацией, регистрацией клиента, обращением к сервису и обработкой решений сервиса. Точки входа Desktop и CLI делят эту реализацию.
- Подтверждение владельца связывает BOX с конкретным существующим разговором. Адрес определяется заново из вызова Codex при каждой операции, а полномочия проверяются на сервисе.
- Отзыв и свежесть проверяются в сервисе. Истечение ожидания, потеря связи и отказ имеют разные результаты. Поздний ответ сохраняет исходную адресацию.
- После проектирования проверены [контракт](contracts/service-boundary.md) и [модель](data-model.md) против FR-001–008. Проверка реального клиента и границы доверия остаётся условием совместимости. Если потоки требуют новых экранов Nearic, их макеты и компоненты проходят отдельное согласование владельцем до реализации.

## Структура проекта

- `cmd/nearic/` — запуск установки для CLI, входа и режима stdio MCP.
- `internal/core/` — OAuth, доступ экземпляра, запросы к Nearic Service и отображаемые исходы.
- `internal/codex/` — чтение метаданных хоста, подтверждение контекста и интеграция MCP.
- `distribution/codex/` — Desktop-манифест и локальный каталог из той же линии выпуска.
- [Исследование](research.md), [модель данных](data-model.md), [граница сервиса](contracts/service-boundary.md) и [проверка клиентов](quickstart.md) — материалы технического ревью.

## Решения для ревью

1. **Граница доверия.** Сервис доверяет зарегистрированному и изолированному хостовому адаптеру. Подпись установки не удостоверяет разговор от имени OpenAI и не защищает от компрометации ОС или её администратора. Если агент может запустить копию адаптера с доступом к тому же ключу или к подписывающему интерфейсу, одной защиты файла правами пользователя недостаточно. При таком результате нужна изоляция либо доверенный интерфейс хоста. Принимать пользовательский ID разговора как замену нельзя.
2. **Клиентская совместимость.** Подтвердить получение метаданных во всех нужных путях вызова, активацию плагина после открытия того же разговора Desktop и поддержку заявленного способа исполнения. Если Desktop требует нового разговора, это блокирует выбранный путь. Любое изменение пользовательского результата выносится владельцу.
3. **Сервис.** Согласовать Device Authorization Grant, привязку разрешения к ключу, подтверждение переключения владельцем, срок ожидания и результат отзыва при запросе в полёте. Предлагается сохранить последнюю привязку для отображения, исключить её из авторизации после отзыва и требовать новое подтверждение при повторном входе. Этот переход согласуется с сервисом.
