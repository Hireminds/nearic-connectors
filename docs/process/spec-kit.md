# Spec Kit: структура и использование

## Карта репозитория

```text
README.md                       назначение и доступные инструкции запуска продукта
CONTRIBUTING.md                  вход для участника и примеры вызова

CLAUDE.md                       подключение общих инструкций для Claude

docs/
  PRODUCT.md                    исходные требования; статус указан в документе
  architecture/                 техническое устройство и границы
  contracts/                    интерфейсы и гарантии взаимодействия
  flows/                        пользовательские сценарии и состояния
  decisions/                    принятые технические решения (ADR)
  process/                      руководства работы и проверки
.agents/skills/
  hireminds-feature/             входной скилл функции в текущем чате
  hireminds-bugfix/              входной скилл исправления ошибки
  hireminds-assess/              входной скилл исследования идеи
  speckit-*/                    официальные инструкции отдельных этапов

  memory/constitution.md        единственный нормативный источник принципов
  templates/                    стандартные шаблоны
  scripts/bash/                 официальные служебные скрипты
```

Продуктовые домены и код сервиса появятся при согласованной
реализации. Настройка инструмента описывается здесь и в CONTRIBUTING, без спек в `specs/`.

## Living Spec

Устойчивые функциональные домены описываются поддерживаемыми `spec.md`. Границы доменов
согласовываются до реализации. При изменении намерения сначала правят контракт, затем
актуализируют производные `plan.md` и `tasks.md`. Последний комплект остаётся рядом;
прошлые версии доступны в Git. Важное обоснование сохраняют в ADR и контрактах до замены плана.

Идентификаторы требований сохраняют; удаление или замена видны в diff. Исправление отклонения
от существующего контракта не требует новой спеки. Draft, согласование и реализация — разные
состояния. Не ослабляйте требование, чтобы объяснить ошибку кода.

Активная директория задаётся локальным `.specify/feature.json` или
`SPECIFY_FEATURE_DIRECTORY`, а не Git-веткой. Назовите агенту нужный домен; он проверит
указатель до выполнения команд. Пока домен не создан, отсутствие активной спеки ожидаемо.
Проверку `check-prerequisites.sh` с требованием spec/plan/tasks запускают после их подготовки.

## Один источник процесса

| Запрос | Скилл чата | Определение |
| --- | --- | --- |
| Новое или изменённое поведение | [hireminds-feature](../../.agents/skills/hireminds-feature/SKILL.md) | [speckit YAML](../../.specify/workflows/speckit/workflow.yml) |
| Ошибка существующего поведения | [hireminds-bugfix](../../.agents/skills/hireminds-bugfix/SKILL.md) | [bugfix YAML](../../.specify/workflows/bugfix/workflow.yml) |
| Исследование до решения о разработке | [hireminds-assess](../../.agents/skills/hireminds-assess/SKILL.md) | [assess YAML](../../.specify/workflows/assess/workflow.yml) |

Порядок, ветвления, review-gates и пределы повторов определяются выбранным YAML с включёнными
overlays. В AGENTS и входных скиллах нет отдельной последовательности. Конституция сохраняет
требования к качеству и полномочиям, а не вторую схему переходов.

Входные скиллы читают определение по [общим правилам чата](chat-workflows.md) и применяют
официальные навыки этапов в текущем разговоре. В этом режиме CLI-run не создаётся.
Runner исполняет то же определение программно, вызывая отдельные CLI-сеансы агента.
Общее описание процесса не делает модельное и программное исполнение тождественными.

При обновлении существующего домена агент сохраняет текущий контракт и меняет запрошенное
поведение. Полный автоматический speckit начинает новый комплект; автоматизированный режим
обновления нескольких доменов отдельно не настроен.

## Что добавлено проектом

Официальные навыки, шаблоны, расширения и базовые YAML не изменены.
[Overlay nearic-quality](../../.specify/workflows/overlays/speckit/nearic-quality.yml)
добавляет проверки функций, передачу отчёта между этапами и цикл по оставшимся задачам.
Его шаги и пределы читают и runner, и входной скилл чата.

Три скилла `hireminds-*` и правила чата написаны для проекта. Это не дополнительные
официальные команды Spec Kit и не плагин Codex desktop. Они остаются автоматически
обнаруживаемыми навыками; отдельная роль тимлида или эксперта не вводится.

## Автоматизация и review

```bash
specify workflow info speckit
specify workflow resolve speckit
specify workflow overlay list speckit
```

Resolve показывает активные слои и атрибуцию шагов, но не выполняет процесс.
Во время run runner сохраняет собственное состояние. Завершённые шаги при resume обычно
не повторяются; действие, прерванное до checkpoint, может выполниться ещё раз.

Review-gates не означают повторного согласования каждого документа владельцем.
Ведущий агент читает результат и может продолжить обычный этап в ранее согласованном
скоупе. Новый существенный выбор требует обсуждения. Не задавайте verdict заранее:

```bash
specify workflow resume RUN_ID --input speckit_review_spec_verdict=approve
specify workflow resume RUN_ID --input speckit_review_plan_verdict=approve
```

Для bugfix доступен `bug_review_assessment_verdict`; исследование завершается review решения
и отдельно согласованной передачей в реализацию.

Ошибки CLI не игнорируются. Отчёт analyze передаётся следующему этапу, но успешный exit code
не означает отсутствия замечаний. Модель обязана устранить блокирующие проблемы или оставить
работу незавершённой. Галочки задач не заменяют сверку кода и реальные тесты.
Проверка `scripts/spec-kit-task-state.py` вычисляет состояние задач для условия YAML;
невалидный список или оставшаяся работа после лимита приводят к ошибке.

## Приватные материалы и проверка

`.specify/feature.json`, `.specify/assessments/`, `.specify/bugs/`,
`.specify/workflows/runs/` и cache исключены из Git. Итоговые исследования, скоупы и отчёты
сохраняются в приватной проектной системе. Автоматической синхронизации с Linear нет.

Команды программных проверок — в [CONTRIBUTING.md](../../CONTRIBUTING.md).
Тесты используют настоящий runner с заглушкой Codex. Смысловое исполнение входного скилла
моделью требует отдельной оценки и не подтверждается этими тестами.
Продуктовые исследования, бренд и оперативная история не копируются в репозиторий.

## Обновление инструмента

Закреплены CLI 1.4.3, bug/assess extensions 1.0.2, workflows speckit 1.0.2, bugfix 1.0.1
и assess 1.0.0. Presets и сторонние workflow не подключены; модель и reasoning не переопределены.

Обновление — отдельное просматриваемое изменение: прочитать release notes, обновить официальный
комплект, проверить integration status, разрешение overlays, входные скиллы и тесты.
Не перезаписывайте проектные файлы неподготовленным init --force.
